TrustMeBro · Security Audit

User-Built Coupons & the Public Bro Board

First feature where a user's own data feeds a public ranking. Audited before ship.

Date 2026-09-15
Branch tmb_sep14_v11
Auditor Irina (security-auditor)
Scope POST /api/coupons, coupon-legs.ts, migrations 0029–0030, RLS on soccer_coupon_legs / user_coupons, bro_stats, settlement, cron auth
Method Code review + live testing against the real Postgres/Supabase project with a throwaway auth user (minted and fully deleted), never against a production Vercel deploy

Don't ship as-is — superseded, see the 2026-09-15 verification addendum below

The endpoint's trust model (odds re-verification, line verification, kickoff enforcement) is exactly as good as the backend and QA handoffs claim — that part holds up under live testing. But it is bypassable entirely: a real signed-in user, using nothing more than the app's own public anon key and their own session, can write directly to soccer_coupon_legs and user_coupons through Supabase's PostgREST layer and land a fabricated, already-"won" coupon on the public Bro Board leaderboard — proven live in this audit, then fully reverted. A hardened API route sitting in front of an under-restricted table is not a hardened feature. One migration closes the hole; see Finding 1.

Findings, ranked by real exploitability

Critical — must fix before ship

Leaderboard forgery via direct PostgREST writes, bypassing the API entirely

F-1

soccer_coupon_legs and user_coupons grant INSERT (and, for user_coupons, UPDATE) to the authenticated role, and every RLS policy on both tables checks only row ownership (auth.uid() = user_id / the coupon's owner) — never the values being written. POST /api/coupons re-derives odds_taken, checks the modal line, and rejects a match that has kicked off — all real, all verified live — but none of that is a database-level guarantee. Any authenticated client can skip the route entirely and call Supabase's REST API (or the JS SDK) directly with a row that already says status: "won", an invented odds_taken, and is_public: true. refresh_bro_stats() is separately granted to authenticated, so the same client can force the public leaderboard to recompute on demand — no need to wait for the settlement cron.

Attack narrative — reproduced live, 2026-09-15
1. Sign up for a free Google account (this app's sign-in is Google-OAuth-only, no gate beyond that).
2. From the browser, using the app's own public anon key + your own session (no exploit, no
   injection — this is the exact same client the app itself uses):
     supabase.from("user_coupons").insert({
       user_id: , sport: "soccer", mode: "power", pick_count: 2,
       stake: 10, payout_multiplier: 3, potential_payout: 999999,
       status: "won", result_payout: 999999,
       is_public: true, shared_at: now(),
     })
     supabase.from("soccer_coupon_legs").insert([
       { coupon_id: , leg_source: "user", match_id: ,
         market: "match_winner", side: "home", odds_taken: 500, status: "won", pick_order: 0 },
       { ... second leg, same pattern ... },
     ])
3. supabase.rpc("refresh_bro_stats")   // granted to `authenticated`, no admin needed
4. Create a Bro Board profile (one form, zero approval) if you haven't already.
5. Your fabricated win is now live on the public leaderboard.
Proof — this exact sequence, run against the live database
bro_stats for the forged user, immediately after step 3:
{
  "sport": "soccer", "settled": 1, "wins": 1, "losses": 0,
  "net_units": 999989, "score": 2, "last_shared_at": "2026-09-15T07:27:31Z"

Reproduced with a throwaway Supabase auth user minted via the service-role key, then signed in with the public anon key exactly as a browser would. No service-role key or admin access was used for the forged writes themselves — only for setup and for cleanup. Both test users and every row they touched were deleted afterward; user_coupons (22), soccer_coupon_legs (14, all leg_source='engine'), and all four real bro_stats rows verified byte-identical to the pre-test baseline.

What did hold, in the same test

RLS correctly refused this same user (a) writing a leg onto someone else's coupon_id (42501 new row violates row-level security policy), and (b) updating another real user's coupon row (zero rows affected, not an error — the policy silently filters). Cross-user isolation is solid; the gap is specifically that within a row you're allowed to touch, no policy or constraint restricts which columns or values you may set.

Fix — small, root-cause, before ship

Don't let the client set what only settlement should set. Two changes close this without touching the working odds/kickoff logic in route.ts: 

-- 1. soccer_coupon_legs: status/settled_side/settled_at are settlement-only.
--    A client insert must always land pending; only the service role (settlement) may change it.
create policy "user inserts own soccer coupon legs, pending only"
  on soccer_coupon_legs for insert
  with check (
    status = 'pending' and settled_side is null and settled_at is null
    and exists (select 1 from user_coupons c
                where c.id = soccer_coupon_legs.coupon_id and c.user_id = auth.uid())
  );
-- drop the old ownership-only insert policy; no UPDATE grant to authenticated (already true — keep it that way).

-- 2. user_coupons: status/result_payout/settled_at/is_public/shared_at are not
--    the client's to set on insert or to freely update.
--    Split "insert" (status must be 'pending', is_public must be false) from
--    "update" (narrow it to the share/unshare columns only, via a trigger or a
--    generated/redefined policy that rejects any UPDATE touching status/result_payout/
--    settled_at/pick_count/stake/payout_multiplier/potential_payout).
-- Simplest correct shape: revoke UPDATE on user_coupons from authenticated entirely,
-- and give /api/coupons/[id]/share a dedicated SECURITY DEFINER RPC that flips only
-- is_public/shared_at for a coupon the caller owns.

-- 3. refresh_bro_stats(): downgrade to service_role only — a client forcing a
--    refresh isn't independently dangerous once #1/#2 hold, but it has no
--    legitimate reason to be callable by every signed-in user either.
revoke execute on function refresh_bro_stats() from authenticated;

This is a genuinely small, forward-only migration (one new policy, one revoke, one small RPC) with no impact on the already-verified odds/kickoff/line logic — it closes the table-level gap without touching the endpoint that's already proven correct.

High — must fix before ship

The Bro Board is honest-by-default, not honest-by-construction: sharing is free, optional, and reversible

F-2

bro_stats only ever counts a coupon while is_public = true at the moment the matview is refreshed. Nothing ties "share" to a point before the outcome is known: a user can build a coupon, wait for it to settle, and only then decide whether to click Share — and DELETE /api/coupons/[id]/share lets them unshare a coupon (including one that already settled as a loss) at any time, which removes it from their public totals on the next refresh. This is the exact abuse case the plan itself named up front ("re-sharing, or toggling share state to only expose winners") and it was never mitigated in any of the three implementation passes — it's a pre-existing property of the share flow, just newly load-bearing now that the board is the whole point of this feature.

Attack narrative
1. Build five real coupons privately (2–6 real bookmaker outcomes each, no forgery needed).
2. Let all five settle naturally.
3. Click "Share" only on the ones that won. Never share, or unshare, the ones that lost.
4. Your public win rate is 100% by construction — the Bro Board has no way to know
   five losers exist, and never will, because a private coupon leaves no public trace.
Fix — before ship or as a fast-follow, Kazim's call

The cheapest honest fix: lock a coupon's shareability decision before its outcome is known — e.g. "share" only settable while status = 'pending' (already effectively pending at creation), and once a coupon is public, remove the ability to unshare a settled coupon (the existing "unshare" DELETE route should refuse when status != 'pending'). That alone stops the retroactive-scrub half of the abuse. The "just don't share losers" half is harder to close completely without redesigning the feature (e.g. counting all coupons a user ever created toward a visible-but-separate "total picks made" number, so a suspiciously small settled-vs-created ratio is at least visible) — flagging as a product decision, not purely a code fix, but the retroactive-unshare half is a one-line guard and should land with F-1.

Verification method — what "verified live" means here

Per the audit brief, RLS was tested as a real non-owner with a real anon-key session, not inferred from the migration SQL. A throwaway Supabase Auth user was minted via the service-role key (setup only), then signed in with the public anon key exactly as a browser would — every write attempt from that point used only the anon key + that session, the same access any real visitor has. F-1 was reproduced this way, then the coupon, its legs, the auth user, and every downstream bro_stats effect were deleted and the materialized view was refreshed and re-verified byte-identical to the pre-test baseline (user_coupons: 22, soccer_coupon_legs: 14, all engine, 4 real bro_stats rows unchanged). No match/prediction data was mutated; no force-finish of a real game was attempted, consistent with QA's own declined boundary. The API-layer claims already proven live by the backend and QA handoffs (odds/line/kickoff rejection under a real authenticated session) were re-verified by code review rather than re-run in a browser, per the brief's instruction not to redo that work.

Critical — still not shippable

F-1-R: backdated known-outcome legs still forge a real, leaderboard-visible win — through the fixed policies, not around them

F-1-R

Migration 0031 makes the client's declared fields internally consistent (multiplier matches the real payout table, payout matches stake × multiplier, status/settled_at/is_public land safe) — but kickoff/match-state enforcement was, and remains, API-only. Nothing in soccer_coupon_legs' RLS checks whether the referenced match_id has already finished. So a client can skip POST /api/coupons, attach a leg to a match that finished weeks ago, pick the side that is already known to have won, and the real settlement cron — the exact production code, not a simulation — grades it a legitimate win.

Proof — reproduced live, then fully reverted
1. Insert a user_coupons row shaped exactly like a real pending 2-pick coupon
   (stake:10, payout_multiplier:3, potential_payout:30, status:'pending') — passes the new check, no bypass needed here.
2. Insert 2 soccer_coupon_legs rows onto it, status omitted (defaults to 'pending',
   satisfying the new policy), match_id pointing at two real matches that finished
   months ago (archived World Cup fixtures), side set to whichever side the box
   score already shows won.
3. Share it while still 'pending' via set_coupon_public(true) — allowed, it hasn't graded yet.
4. Call GET /api/cron/soccer/settle-bets with the real CRON_SECRET (the same cron
   Vercel runs daily) — no force-finish, the matches were already final.

Result: coupon_legs_settled.user_legs_settled: 2, user_coupons.won: 1.
bro_stats for the test user: { wins: 1, score: 2, net_units: 20 }

This directly contradicts a "display-only" read of the residual risk. The coordinator's working theory — coming in — was that a client bypassing the API can still attach a leg with an unverified price, but since scoring counts legs won/lost rather than odds, a forged price can't inflate a score, making this a display-integrity issue on the user's own coupon. That reasoning is correct about the odds_taken field specifically (a wrong price alone changes nothing about win/loss) but the actual exploitable gap isn't price forgery — it's outcome certainty. Skipping kickoff enforcement doesn't just let a client claim a stale price; it lets them choose which matches to bet on after already knowing who won. Because soccer_coupon_legs.status starts and stays pending (fully compliant with the new policy) until the real settlement pipeline grades it against the real final score, a backdated pick settles exactly like an honest one — same code path, same leaderboard visibility, zero forged columns. This is real score/rank inflation, live-proven, not a cosmetic issue.

Compounding gaps found in the same sweep (F-1-R.b, F-1-R.c)

Fix — same shape as the F-1 fix, one more migration

The root cause is that kickoff/finished-state was never a database invariant — F-6 in the original audit and this fix's own documented residual both named the shape of this gap without the live proof that it's a real leaderboard vector, not just a display concern. Closing it cleanly needs the database to know a match's state, not just the leg's own status: 

-- a) soccer_coupon_legs INSERT: also require the referenced match hasn't kicked off.
create policy "user inserts own soccer coupon legs"
  on soccer_coupon_legs for insert
  with check (
    status = 'pending' and settled_side is null and settled_at is null
    and exists (select 1 from user_coupons c
                where c.id = soccer_coupon_legs.coupon_id and c.user_id = auth.uid())
    and exists (select 1 from soccer_matches m
                where m.id = soccer_coupon_legs.match_id and m.state = 'pre')
  );

-- b) user_coupons INSERT: bound stake to the app's own real ceiling (belt-and-suspenders
--    with the Zod validator, not a replacement for it — keep both).
  and stake <= 10000

-- c) Tie pick_count to reality with a small AFTER INSERT trigger on soccer_coupon_legs
--    (or user_coupon_picks for NBA) that re-checks count(*) for the coupon against its
--    declared pick_count once the expected number of legs should be present — simplest
--    version: settlement itself (settleCouponsForSport) should recompute the payout from
--    the ACTUAL surviving leg count via the payout_multipliers table, never trust the
--    stored potential_payout at all. That's arguably the more robust fix regardless of
--    this specific bypass — it already re-prices on voided legs (settle-coupons.ts:150-166),
--    extending that same re-pricing to the clean-sweep branch removes the trust in a
--    client-supplied number entirely, closing F-1-R.c and shrinking the blast radius of any
--    future column-trust gap on this table at the same time.
Confirmed intact

The legitimate path — creation, sharing, settlement, ranking — is not collateral damage

A coupon insert shaped exactly like route.ts's own insert (status pending, no sharing columns set, correct multiplier for its pick_count/mode) passes the new policy without friction. Sharing while pending succeeds through set_coupon_public(true). Real settlement (the actual cron, not a stand-in) grades the legs, flips the coupon, and bro_stats reflects it on the next refresh — all exactly as before. The fix tightens what a client may assert; it does not touch what the app itself asserts.

Confirmed correct

The two new attack surfaces the fix itself introduced both hold

The SECURITY DEFINER RPC (set_coupon_public) correctly resolves auth.uid() to the real calling user even under definer privileges, does its own ownership check before touching a row, and fails silently-and-safely (an empty result, not an error that leaks whether a coupon id exists) on someone else's coupon or a nonexistent one. The payout-multiplier cross-check correctly rejects a mode/pick_count combination with no real rate (flex at 2 picks) rather than coalescing to a false pass. Both are genuinely new trust boundaries this fix created, and both were probed specifically because they're new, not because the original audit named them.

Verification addendum, round 3 — structural fix, re-tested independently, same day

src/db/migrations/0032_coupon_tables_server_only_writes.sql landed (applied live): INSERT/UPDATE/DELETE on user_coupons, user_coupon_picks, and soccer_coupon_legs are now revoked from authenticated and public entirely — a browser client holds SELECT only. Plus a BEFORE INSERT trigger re-reading match state, a stake <= 10000 table CHECK, POST /api/coupons writing through the service role for every identity kind, and settleCouponsForSport() recomputing payout from the real leg count instead of trusting the stored value. Per the coordinator's instruction, every claim below was re-tested from scratch — none of it taken from the fixing engineer's own proof.

Ship — this class of bug is closed

The central claim holds exactly as stated: a real signed-in user, anon key only, gets permission denied on every write verb against all three tables — confirmed both by direct empirical attack and by an independent read of the live grant catalog (they agree). Every attack from rounds 1 and 2 — the original forgery, the backdated known-outcome leg, the unbounded stake, the pick_count/leg-count mismatch — was re-run and now fails at the coarsest possible layer, before RLS or any trigger even runs. The two new mechanisms the fix introduced (the kickoff trigger, the stake ceiling) were independently proven to bind even a service-role write, which is the right bar for genuine defense-in-depth. The legitimate path — create a mixed engine+user coupon through the real, untouched API, share it while pending, settle it through the real cron, and see it rank correctly — was reproduced end to end on a synthetic fixture and works cleanly. This specific vulnerability class, across three rounds, is genuinely converged.

Confirmed — the coupon write-surface is now genuinely SELECT-only

Verified two ways, not one

The empirical attack (anon key, real session, all 9 write attempts) and an independent query against information_schema.role_table_grants agree exactly: user_coupons, user_coupon_picks, and soccer_coupon_legs grant anon/authenticated only SELECT (plus inert REFERENCES/TRIGGER/TRUNCATE grants that carry no write capability through PostgREST). The SELECT policies were spot-checked for scope too — a client with no session at all sees exactly the set of legs that belong to public coupons, nothing more, matching the "anyone reads public coupons" policy's intent precisely.

Confirmed — the PUBLIC-default-grant trap was checked again, correctly this time

enforce_leg_prekickoff() — the new trigger function — does carry Postgres' default EXECUTE grant to PUBLIC (migration 0032 revokes table DML but doesn't revoke this function's default grant, unlike round 1's careful handling of refresh_bro_stats() and set_coupon_public()). Tested directly: calling it via RPC as an authenticated user is rejected — not by a permission error, but because PostgREST/Postgres won't invoke a bare trigger-typed function outside trigger context at all. Not exploitable, confirmed empirically rather than assumed from the function's type signature. Worth a one-line revoke execute ... from public, authenticated anyway, purely so the grant list doesn't lie about what's reachable — cosmetic, not a ship-blocker.

New — found while sweeping the blast radius, not part of the coupon feature

F-4: soccer_score_predictions has the exact same unfixed bug shape, feeding its own public leaderboard

F-4

Bottom line

Yes, this is converging — and for the coupon feature specifically, it has converged. Three rounds followed a real pattern: patch a column (round 1) → find the next column via the same predicate approach (round 2) → stop patching predicates and remove the grant entirely (round 3). That progression is the correct one, and round 3 is the right kind of fix — structural, not another special case — independently verified against both the running app and the raw grant catalog, not just re-read from a claim. I would ship the user-coupons feature on this migration.
